# Backends

A backend is a thin adapter between this library and one driver. It owns the
five things that genuinely differ between databases:

1. how you connect;
2. what a parameter placeholder looks like;
3. how you quote an identifier;
4. how you write an upsert;
5. which errors are worth retrying.

Everything else - pooling, transactions, chunking, redaction, retry, progress
reporting - lives in the shared layer and is written once.

## Support matrix

| Backend | Driver | Extra | Bulk copy | Upsert | Streaming | Transactions |
|---------|--------|-------|-----------|--------|-----------|--------------|
| `sqlite` | `sqlite3` (stdlib) | none | no | yes | yes | yes |
| `postgres` / `postgresql` | `psycopg` or `psycopg2` | `postgres` | yes - `COPY FROM STDIN` | yes | yes - server-side cursor | yes |
| `mysql` / `mariadb` | `mysql-connector-python` | `mysql` | yes - `LOAD DATA LOCAL INFILE` | yes | yes - unbuffered cursor | yes |
| `oracle` | `python-oracledb` | `oracle` | no - `executemany` **is** array DML | yes | yes - prefetch tuned | yes |
| `snowflake` | `snowflake-connector-python` | `snowflake` | yes - `PUT` + `COPY INTO` | yes | yes | yes |
| `adls` / `azure_blob` | `azure-storage-blob` | `azure` | n/a - object storage | no | n/a | no |

Install one, several or all:

```bash
pip install "pydb-connect[postgres]"
pip install "pydb-connect[postgres,snowflake]"
pip install "pydb-connect[all]"
```

`sqlite` needs nothing - it is the standard library, and it is what the tests and
examples run on.

Check what a given machine actually has:

```bash
pydb config list --backends
```

## Placeholder styles

| Backend | Style | Renders | Example |
|---------|-------|---------|---------|
| `sqlite` | `qmark` | `?` | `WHERE id = ?` |
| `postgres` | `format` | `%s` | `WHERE id = %s` |
| `mysql` | `format` | `%s` | `WHERE id = %s` |
| `snowflake` | `format` | `%s` | `WHERE id = %s` |
| `oracle` | `numeric` | `:1`, `:2` | `WHERE id = :1` |

All three styles bind **positionally**, which is why the bulk layer can always
pass tuples and never has to know which backend it is talking to. When you write
SQL by hand you do have to use the right style for that backend - or generate it
with `backend.placeholders(n)`:

```python
backend = conn.backend
sql = f"INSERT INTO t (a, b) VALUES ({backend.placeholders(2)})"
```

## Upsert dialects

Generated by `backend.upsert_sql(table, columns, key_columns, update_columns)`.
Each binds every value exactly once, so all of them work with `executemany`.

**SQLite and PostgreSQL** - `ON CONFLICT`, requires a unique index on the keys:

```sql
INSERT INTO "t" ("id", "name") VALUES (?, ?)
ON CONFLICT ("id") DO UPDATE SET "name" = excluded."name"
```

PostgreSQL resolves the conflict target against an **index**, not against column
names. Without a unique constraint you get `there is no unique or exclusion
constraint matching the ON CONFLICT specification`.

**MySQL** - `ON DUPLICATE KEY UPDATE`:

```sql
INSERT INTO `t` (`id`, `name`) VALUES (%s, %s)
ON DUPLICATE KEY UPDATE `name` = VALUES(`name`)
```

MySQL matches on *any* unique key, not the one you named. With two unique
indexes it can update a row you did not intend to touch. `VALUES()` is used
rather than the 8.0.19+ row alias so the statement also works on 5.7 and MariaDB.

**Oracle** - `MERGE` against `dual`:

```sql
MERGE INTO "T" tgt USING (SELECT :1 AS "ID", :2 AS "NAME" FROM dual) src
ON (tgt."ID" = src."ID")
WHEN MATCHED THEN UPDATE SET tgt."NAME" = src."NAME"
WHEN NOT MATCHED THEN INSERT ("ID", "NAME") VALUES (src."ID", src."NAME")
```

Oracle forbids updating a column in the `ON` clause, so key columns are excluded
from the update list automatically.

**Snowflake** - `MERGE` with a `FROM`-less `SELECT`:

```sql
MERGE INTO "T" tgt USING (SELECT %s AS "ID", %s AS "NAME") src
ON (tgt."ID" = src."ID")
WHEN MATCHED THEN UPDATE SET tgt."NAME" = src."NAME"
WHEN NOT MATCHED THEN INSERT ("ID", "NAME") VALUES (src."ID", src."NAME")
```

For very large merges on Snowflake, load to a staging table with `copy_from` and
issue one `MERGE` against it. Row-at-a-time `MERGE` is correct but not how
Snowflake wants to be used at scale.

## Bulk copy, honestly

`copy_from()` uses the native path where one exists and falls back to chunked
`executemany` where it does not. The fallback is reported in
`BulkResult.method`, so a load that quietly got ten times slower is visible
rather than mysterious. Pass `fallback=False` to make it an error instead.

**PostgreSQL** - real `COPY ... FROM STDIN`, rows streamed as CSV, never parsed
as SQL. Typically 5-20x `executemany`. This is the reason to reach for
`copy_from` at all.

**Snowflake** - rows written to a local gzipped CSV, `PUT` to the table's
internal stage, then `COPY INTO ... PURGE = TRUE`. The designed bulk path, and
dramatically faster above roughly 100k rows. Below that the staging overhead
dominates and plain `bulk_insert` wins. Requires a real table: `@%table` does
not exist for views.

**MySQL** - `LOAD DATA LOCAL INFILE`. Needs `local_infile=ON` on the server and
`allow_local_infile=True` in `options`. Many managed MySQL services disable it,
in which case the driver raises and the fallback takes over.

**Oracle** - no `COPY`, and none is needed. `oracledb`'s `executemany` is *array
DML*: the whole batch crosses to the server in one call and is applied in a
single context switch. `bulk_insert` is the fast path on Oracle, not a
consolation prize.

**SQLite** - no bulk loader. `executemany` with a transaction per chunk is as
good as it gets, and it is fast.

## Streaming

`Connection.stream()` and `bulk.chunked_read()` keep memory proportional to
`chunk_size` rather than to result size. What "server-side" means per backend:

- **PostgreSQL** - a named cursor. Genuinely server-side: without it, libpq
  buffers the entire result in client memory before the first row arrives, which
  is why "the query is fast but Python gets OOM-killed" is such a common
  PostgreSQL story.
- **MySQL** - an unbuffered cursor. Rows are read from the socket as consumed.
  You must finish reading before running another statement on that connection.
- **Oracle** - cursors are server-side already; `arraysize` and `prefetchrows`
  are raised to 5000 for streaming, which is the single biggest win available
  when reading a large table from Oracle.
- **Snowflake and SQLite** - the driver chunks with `fetchmany`. Memory in your
  process stays bounded either way.

## Per-backend configuration

### sqlite

```yaml
backend: sqlite
database: ./warehouse.db        # or ':memory:'
options:
  timeout: 10.0                 # seconds to wait on a locked database
  journal_mode: WAL             # strongly recommended for any concurrency
  foreign_keys: true            # OFF by default in SQLite, which surprises people
  busy_timeout: 5000            # milliseconds
```

### postgres

```yaml
backend: postgres
host: db.internal
port: 5432
database: analytics
schema: reporting               # applied as SET search_path
user: etl_writer
secret: env:PGPASSWORD
options:
  sslmode: require
  application_name: nightly-load   # shows up in pg_stat_activity
  connect_timeout: 10
```

`psycopg` (v3) is preferred; `psycopg2` is used if that is what is installed.

### mysql

```yaml
backend: mysql
host: mysql.internal
port: 3306
database: orders
user: etl
secret: env:MYSQL_PASSWORD
options:
  charset: utf8mb4              # use this, not 'utf8', which is 3-byte
  connection_timeout: 10
  allow_local_infile: true      # required for copy_from
```

### oracle

```yaml
backend: oracle
host: ora.internal
port: 1521
database: ORCLPDB1              # service name
schema: STAGING                 # ALTER SESSION SET CURRENT_SCHEMA
user: ETL_USER
secret: env:ORACLE_PASSWORD
options:
  dsn: ora.internal:1521/ORCLPDB1   # or a full DSN / TNS alias
  thick: false                      # thin mode needs no Instant Client
  arraysize: 5000
```

### snowflake

```yaml
backend: snowflake
database: ANALYTICS
schema: PUBLIC
user: ETL_SVC
secret: env:SNOWFLAKE_PASSWORD
options:
  account: ab12345.eu-west-1    # required
  warehouse: LOAD_WH
  role: TRANSFORMER
  private_key_file: /run/secrets/rsa_key.p8   # key-pair auth; secret is the passphrase
```

Key-pair auth is preferred for service accounts, and Snowflake is progressively
requiring it. Keep `pool.recycle` well under the warehouse auto-suspend
interval, and do not hold transactions open across long Python work - it holds
locks and it costs money.

### adls

Object storage, not SQL. `execute`, `query` and `upsert` raise
`NotSupportedError` with a message pointing at the right method.

```yaml
backend: adls
host: mystorageacct             # or a full https:// URL
database: raw                   # container / filesystem name
secret: env:AZURE_STORAGE_CONNECTION_STRING   # optional
options:
  auth: default                 # default | connection_string | key | sas
  endpoint_suffix: core.windows.net
```

```python
with connect("lake") as lake:
    client = lake.client
    for path in client.list_paths("events/2026/"):
        print(path, client.stat(path)["size"])
    data = client.read_bytes("events/2026/01/part-0.parquet")
    client.upload_file("/tmp/out.parquet", "curated/out.parquet")
    client.write_text("_SUCCESS", "")
```

With no `secret`, `DefaultAzureCredential` is used - managed identity, workload
identity, or your `az login` session. That is the right answer wherever it is
available: nothing to store, nothing to rotate. When a `secret` is present and
`auth` is `default`, its shape is detected: `AccountKey=` means a connection
string, a leading `?` or an embedded `sig=` means SAS, anything else is treated
as an account key.

Directory operations (`create_directory`, `rename`, `delete_directory`) need a
hierarchical namespace and `azure-storage-file-datalake`, loaded on first use.

## Error classification

Each backend maps driver errors to "retry" or "do not retry" using real error
**codes**, not string matching. This is what stops a retry loop from hammering a
database over a typo.

| Backend | Retried | Never retried |
|---------|---------|---------------|
| `sqlite` | `database is locked`, `busy` | `IntegrityError`, `ProgrammingError` |
| `postgres` | SQLSTATE `08*` connection, `40001` serialisation, `40P01` deadlock, `53*` resources, `57P01` admin shutdown | `23505` duplicate key, `42601` syntax, `42P01` missing table, `28P01` bad password |
| `mysql` | `2006` server gone away, `2013` lost connection, `1213` deadlock, `1205` lock wait, `1040` too many connections | `1062` duplicate entry, `1064` syntax, `1045` access denied, `1146` missing table |
| `oracle` | `ORA-03113/03114` end-of-file, `ORA-12170` TNS timeout, `ORA-12541` no listener, `ORA-00060` deadlock | `ORA-00001` unique constraint, `ORA-00904` invalid identifier, `ORA-00942` table missing, `ORA-01017` bad credentials |
| `snowflake` | `250001` connection closed, `390114` token expired, network errors | Compilation errors, `390100` auth failures |
| `adls` | HTTP `429` throttled, `503` busy, `500`, `502`, `504` | `400`, `401`, `403`, `404`, `409`, `412` |

A backend returns `True`, `False`, or `None` for "no opinion", in which case the
generic classifier in `pydbconnect.retry` decides. Some types are never
retryable no matter what a backend says - `TypeError`, `ValueError`,
`ConfigurationError`, `UnsafeSQLError` - because retrying a bug cannot help.

Unknown errors default to **not retryable**. Retrying something you do not
understand, against a database other people share, is how a small incident
becomes a large one.

## Adding a backend

Roughly 150 lines. Here is a complete one for DuckDB.

**1. Create the module** at `pydbconnect/backends/duckdb.py`:

```python
"""DuckDB backend."""

from __future__ import annotations

from typing import TYPE_CHECKING, Any, Optional, Sequence

from ..exceptions import ConnectionFailure
from .base import Backend

if TYPE_CHECKING:
    from ..config import ConnectionConfig


class DuckDBBackend(Backend):
    """DuckDB via the ``duckdb`` package."""

    name = "duckdb"
    driver_module = "duckdb"        # imported lazily, never at module level
    install_extra = "duckdb"
    default_port = None
    required_fields = ("database",)

    placeholder_style = "qmark"
    quote_char = '"'
    supports_copy = False
    supports_upsert = True
    supports_streaming = True
    supports_transactions = True

    def connect(self, config: "ConnectionConfig") -> Any:
        duckdb = self.import_driver()          # raises a message naming the extra
        try:
            return duckdb.connect(config.database, **(config.options or {}))
        except Exception as exc:
            raise ConnectionFailure(
                f"cannot open duckdb database {config.database!r}: {exc}",
                connection=config.name,
            ) from exc

    def ping(self, conn: Any) -> bool:
        try:
            conn.execute("SELECT 1").fetchone()
        except Exception:
            return False
        return True

    def upsert_sql(self, table, columns, key_columns, update_columns=None) -> str:
        updates = self.merge_update_columns(columns, key_columns, update_columns)
        insert = self.insert_sql(table, columns)
        conflict = ", ".join(self.quote_identifier(k) for k in key_columns)
        if not updates:
            return f"{insert} ON CONFLICT ({conflict}) DO NOTHING"
        sets = ", ".join(
            f"{self.quote_identifier(c)} = excluded.{self.quote_identifier(c)}"
            for c in updates
        )
        return f"{insert} ON CONFLICT ({conflict}) DO UPDATE SET {sets}"

    def classify_error(self, exc: BaseException) -> Optional[bool]:
        name = type(exc).__name__
        if name in ("ConstraintException", "ParserException", "BinderException"):
            return False
        if name in ("IOException", "ConnectionException"):
            return True
        return None                            # no opinion; generic rules decide
```

**2. Register it.** Either add it to `BUILTIN_BACKENDS` in `registry.py`:

```python
"duckdb": "pydbconnect.backends.duckdb:DuckDBBackend",
```

or, for a backend that lives in your own package, register it at import time:

```python
from pydbconnect.registry import register_backend
from mypackage.backends import DuckDBBackend

register_backend(DuckDBBackend)          # uses DuckDBBackend.name
```

**3. Add the extra** to `pyproject.toml`:

```toml
[project.optional-dependencies]
duckdb = ["duckdb>=0.10"]
```

**4. Test it.** The shared behaviour is already covered; test what is yours:

```python
def test_duckdb_upsert_dialect():
    backend = get_backend("duckdb")
    sql = backend.upsert_sql("t", ["id", "name"], ["id"])
    assert "ON CONFLICT" in sql and "excluded" in sql

def test_duckdb_classifies_constraint_errors():
    class ConstraintException(Exception): pass
    assert get_backend("duckdb").classify_error(ConstraintException("dup")) is False
```

### Rules

- **Import the driver inside the method that needs it**, via
  `self.import_driver()`. A top-level `import duckdb` makes the whole library
  uninstallable for someone who only uses MySQL, and it is checked by a test.
- **Return a DB-API 2.0 connection** from `connect()`. If your driver is not
  DB-API, return an adapter providing `cursor()`, `commit()`, `rollback()` and
  `close()` - see `adls.py`, which raises `NotSupportedError` from `cursor()`
  and makes the object-store methods available on `connection.client`.
- **`ping()` must never raise.** It runs on every pool checkout. Return `False`.
- **Prefer error codes over message matching** in `classify_error`. Return
  `None` when you do not know; the generic classifier already does string
  matching as a fallback.
- **Never log, `repr` or embed a credential.** Pass `SecretStr.reveal()`
  straight into the driver call and nowhere else.
- **Backends are stateless and shared.** The registry keeps one instance per
  name; do not store per-connection state on `self`.
